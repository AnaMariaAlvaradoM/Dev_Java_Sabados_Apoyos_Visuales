02 · CampusFlow

¿Qué hace que un software sea SaaS?

Concepto central 1 · El proveedor opera el servicio.

Entrega por internet

El cliente accede a la plataforma; no tiene que instalar ni administrar el backend.

Operación continua

El proveedor mantiene, actualiza y opera el software que los clientes utilizan.

Acceso y planes

La suscripción es frecuente. También puede haber acceso gratuito: pagar cada mes no es la definición completa de SaaS.

Conecta con un servicio que uses

Una academia usa CampusFlow por internet. ¿Qué recibe y qué responsabilidades conserva el proveedor?

Comprobar razonamiento

La academia recibe acceso a la gestión de cursos. El proveedor opera la plataforma y mantiene el servicio. La academia administra su uso y sus datos según los permisos del producto.

i

CampusFlow: el producto previsto y la base de hoy

El producto ofrecerá acceso continuo a la gestión de cursos. Hoy construimos su base de backend: todavía no hay pagos ni suscripciones. Organizar código por dominios facilita la evolución, pero no convierte por sí solo el prototipo en un servicio listo para vender.

Monolito modular

Todo se despliega junto. Los paquetes no son microservicios independientes. common reúne excepciones compartidas; application*.properties vive en src/main/resources. Hoy no creamos un paquete Java config.

Una necesidad pendiente

Comprobar razonamiento

No. Cada academia es un tenant y necesita datos y permisos delimitados. Esa pregunta sigue abierta para la Clase 14; hoy solo identificamos la necesidad.

package com.devsenior.campusflow.common.exception;

import java.util.Map;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<Map<String, String>> manejarNoEncontrado(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(Map.of("error", ex.getMessage()));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<Map<String, String>> manejarGeneral(Exception ex) {
        log.error("Error no controlado al procesar la petición", ex);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(Map.of("error", "Ocurrió un error interno. Intenta de nuevo."));
    }
}

Dos ideas para continuar construyendo

Ahora puedes explicar el producto y la organización de su backend.

1 · SaaS

El proveedor opera el software y lo entrega por internet, con acceso continuo y planes que pueden ser gratuitos o pagos.

2 · Arquitectura modular

Los módulos reúnen capacidades de negocio. Sus capas separan HTTP, casos de uso y persistencia; sus límites requieren dependencias explícitas.

  • Problema trabajado: localizar cambios y separar responsabilidades al crecer CampusFlow.
  • Resultado: un listado de usuarios organizado por dominio, perfiles de entorno y manejo compartido de errores. Cursos extiende el mismo patrón.

i

validate no crea tablas

En desarrollo update puede modificar el esquema. En producción validate comprueba tablas existentes; Flyway o Liquibase pueden gestionarlas mediante migraciones versionadas. No instalamos estas herramientas hoy.

El perfil lo decide el ambiente en esta práctica

Elegimos SPRING_PROFILES_ACTIVE fuera del repositorio. Spring también admite spring.profiles.active en configuración base; no se coloca dentro de los propios archivos de perfil. Es una decisión de configuración, no una regla que prohíba todos los archivos.

Límites de la respuesta de errores

Las excepciones MVC heredadas pueden devolver ProblemDetail, mientras que los handlers propios usan el mapa error. Unificar ese contrato queda pendiente. El advice no captura errores de arranque ni todos los filtros de seguridad.

Buenas prácticas para la evolución

Usar DTOs cuando la entidad incluya datos sensibles; versionar la API antes de tener clientes externos; mantener paquetes en minúsculas y una convención consistente. CampusFlow usa usuarios y cursos en plural. No se añaden hoy esas funcionalidades.
