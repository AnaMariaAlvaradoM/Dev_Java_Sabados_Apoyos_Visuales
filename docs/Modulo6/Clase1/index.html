Decidir · 03

Alcance realista: el MVP

3.1 · El error más caro de un proyecto

La mayoría de proyectos no fracasan por el código. Fracasan porque intentan hacer todo y no terminan nada.

Definición técnica

(Producto Mínimo Viable): la versión más pequeña del producto que resuelve el problema principal de un usuario real y permite comprobar si vale la pena seguir invirtiendo.

En la vida real

Un restaurante que abre no arranca con 80 platos. Abre con 8 que salen bien, mira cuáles se piden y después amplía la carta.

3.2 · La técnica MoSCoW

Es una forma de clasificar requisitos en cuatro cajas:

Caja Significado Pregunta para decidir
Must Debe estar ¿Sin esto el producto no resuelve el dolor?
Should Debería estar ¿Es importante, pero se puede vivir una semana sin esto?
Could Podría estar ¿Es un "qué bueno sería"?
Won't (por ahora) No en esta versión ¿Es otro producto o otro presupuesto?

3.3 · Clasificamos el correo de Patricia

Pedido de Patricia Caja Por qué
Registrar clientes y solicitudes Must Sin esto no hay nada que cotizar
Catálogo de materiales con precios Must La IA necesita precios reales; no puede inventarlos
Borrador de cotización con IA Must Es lo que reduce de 2 días a minutos
Patricia revisa y aprueba Must La IA propone, una persona decide
Métricas de aprobación y materiales Should Útil, pero no recupera clientes la primera semana
Pago en línea Could Ya lo hicimos con Stripe; se suma después
Contabilidad y app de instaladores Won't (por ahora) Son otros productos
Para pensar

Si dejas "aprobar la cotización" por fuera y la IA envía el borrador directo al cliente, ¿qué riesgo corres?

Comprobar

Que el cliente reciba un precio equivocado como si fuera una promesa del taller. Un modelo de lenguaje puede inventar una medida o un material. Por eso la aprobación humana es Must, no un adorno.

Criterio de alcance

Una regla práctica: si una funcionalidad no aparece en la frase "solicitud → borrador → aprobación → envío", no entra al MVP.

Decidir · 04

Arquitectura enterprise inicial

4.1 · La decisión grande

Ya tenemos el qué. Ahora: ¿cómo organizamos el código para que crezca sin volverse un nudo?

Definición técnica

Monolito modular: una sola aplicación que se despliega como una unidad, pero cuyo código se organiza en módulos de negocio con límites claros. Cada módulo es dueño de sus datos y expone solo lo necesario.

En la vida real

Un edificio de oficinas: una sola construcción, un solo contador de luz. Pero cada empresa tiene su piso, su puerta y su llave. Nadie entra a la oficina de otro a mover papeles.

4.2 · Paquetes por módulo, no por capa

En los Módulos 3 y 4 organizamos por capa: controller, service, repository. Desde Atiende cambiamos a paquetes por funcionalidad. Hoy lo hacemos con intención desde el primer día.

Referencia
com.devsenior.cotiza
├── cliente        → quién pide
├── catalogo       → materiales y precios del taller
├── solicitud      → el mensaje original del cliente
├── cotizacion     → el borrador, sus ítems y su estado
├── ia             → conversación con Gemini (con fallback)
└── comun          → lo que comparten todos (estado, errores)

Por qué así

Si mañana cambia la forma de cotizar, todo vive en cotizacion. Si cambiamos Gemini por otro modelo, solo se toca ia. Eso es el principio de responsabilidad única (la "S" de SOLID), aplicado a paquetes.

Para pensar

Mañana Patricia pide guardar el valor del transporte de cada mueble. ¿En qué paquete va?

Comprobar

En cotizacion: el transporte es un valor de cada cotización, no del catálogo ni algo que compartan todos los módulos.

4.3 · El flujo del MVP

Referencia
Cliente escribe → POST /api/solicitudes
        ↓
solicitud guarda el mensaje
        ↓
ia arma un borrador con precios de catalogo  (si falla → borrador vacío)
        ↓
cotizacion queda en BORRADOR
        ↓
Patricia ajusta y aprueba → APROBADA
        ↓
Se envía al cliente → ENVIADA

Roadmap, sprint y criterios de calidad

6.1 · Roadmap: el mapa del mes

Definición técnica: un roadmap ordena en el tiempo los entregables del producto, de modo que cada etapa entregue algo que se pueda probar. En la vida real: construir una casa: primero cimientos, después muros, después acabados. Nadie pinta antes de tener paredes.

Etapa Qué entrega Cuándo
Sprint 0 Proyecto, reglas, README y el módulo cliente Hoy (Clase 21)
Sprint 1 Catálogo, solicitudes, borrador con IA, aprobación, tests y deploy Clase 22
Después del curso Métricas, pagos con Stripe, envío por WhatsApp Backlog

6.2 · Sprint

Definición técnica: un periodo corto y fijo (normalmente 1 o 2 semanas) en el que el equipo se compromete a terminar un conjunto pequeño de trabajo. En la vida real: una lista del mercado para esta semana: no compras para todo el año.

Sprint 0 es el sprint de preparación: dejar el terreno listo para que el trabajo de los siguientes sprints fluya.

6.3 · Definición de Hecho (Definition of Done)

Definición técnica: la lista de condiciones que toda funcionalidad debe cumplir para considerarse terminada. Es igual para todas las tareas. En la vida real: el control de calidad de una fábrica de muebles: ningún clóset sale si no tiene bisagras ajustadas, puertas alineadas y bordes lijados.

# Cotiza

Backend de cotizaciones con IA para talleres de muebles a la medida.

**Estado:** 🚧 Sprint 0 · versión 0.1.0

## El problema
Roble & Pino tarda 1 o 2 días en responder cada cotización y pierde clientes.
Cotiza arma un borrador con IA usando los precios del taller; una persona lo revisa y lo envía el mismo día.

## Stack
Java 17 · Spring Boot 4.1.1 · Maven · MySQL · Gemini

1. Crea un usuario de MySQL y pon sus datos en `src/main/resources/application.properties`.
2. Ejecuta `CotizaApplication`.
3. Abre `http://localhost:8080/api/estado`.

|---|---|---|
| GET | `/api/estado` | Confirma que el servicio está activo |
| POST | `/api/clientes` | Registra un cliente |
| GET | `/api/clientes` | Lista los clientes |
| GET | `/api/clientes/{id}` | Busca un cliente |

## Roadmap
- [x] Sprint 0: proyecto, reglas y clientes
- [ ] Sprint 1: catálogo, solicitudes, borrador con IA, aprobación y deploy

El agente construye Clientes

10.1 · Pedir con una especificación, no con un deseo

Momento IANivel 3Agente de Cursor

Qué razonas primero tú: los campos del cliente, qué es obligatorio y qué respuesta esperas en cada caso.

Prompt sugerido
Lee AGENTS.md. Crea el módulo `cliente`: entidad Cliente (nombre obligatorio de máx. 120 caracteres, teléfono obligatorio de 10 dígitos y único, correo opcional pero válido, fecha de creación automática), repositorio, DTOs ClienteRequest y ClienteResponse como record, servicio y controlador con POST /api/clientes (201), GET /api/clientes y GET /api/clientes/{id} (404 si no existe). Si el teléfono ya existe, responde 409. No toques otros paquetes. Al terminar, dime qué archivos creaste.

Cómo validar la respuesta: recorre la Definición de Hecho punto por punto (abajo) y prueba en Postman los cinco casos de la tabla. Qué NO se delega: decidir qué es obligatorio, que el teléfono sea único, ni aprobar el resultado.

10.4 · El error que dejamos abierto a propósito

Mira la respuesta del caso 3. El código 400 es correcto, pero el cuerpo solo dice "error":"Bad Request". No dice qué campo falló. El caso 2 tampoco muestra el mensaje "Ya existe un cliente con ese teléfono".

Para pensar

Mandaste un nombre vacío y un teléfono de 3 dígitos. La API responde 400 sin más detalle. ¿Esto cumple la Definición de Hecho?

Comprobar

Cumple la letra ("responde 400"), pero no sirve a quien consume la API: no sabe qué corregir. Spring Boot esconde por defecto el detalle de los errores para no filtrar información interna. La solución es un manejador global de errores con un formato propio, y es lo primero del Sprint 1.

package com.devsenior.cotiza.cliente;

import java.time.LocalDateTime;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.PrePersist;
import jakarta.persistence.Table;

@Entity
@Table(name = "clientes")
public class Cliente {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String nombre;

    @Column(nullable = false, length = 20)
    private String telefono;

    @Column(length = 120)
    private String correo;

    @Column(nullable = false, updatable = false)
    private LocalDateTime fechaCreacion;

    protected Cliente() {
    }

    public Cliente(String nombre, String telefono, String correo) {
        this.nombre = nombre;
        this.telefono = telefono;
        this.correo = correo;
    }

    @PrePersist
    void alCrear() {
        this.fechaCreacion = LocalDateTime.now();
    }

    public Long getId() {
        return id;
    }

    public String getNombre() {
        return nombre;
    }

    public String getTelefono() {
        return telefono;
    }

    public String getCorreo() {
        return correo;
    }

    public LocalDateTime getFechaCreacion() {
        return fechaCreacion;
    }
}

CrearClienteService.java
package com.devsenior.cotiza.cliente;

import java.util.List;

import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.web.server.ResponseStatusException;

import com.devsenior.cotiza.cliente.dto.ClienteRequest;
import com.devsenior.cotiza.cliente.dto.ClienteResponse;

@Service
public class ClienteService {

    private final ClienteRepository clienteRepository;

    public ClienteService(ClienteRepository clienteRepository) {
        this.clienteRepository = clienteRepository;
    }

    public ClienteResponse crear(ClienteRequest request) {
        if (clienteRepository.existsByTelefono(request.telefono())) {
            throw new ResponseStatusException(HttpStatus.CONFLICT, "Ya existe un cliente con ese teléfono");
        }
        Cliente cliente = new Cliente(request.nombre(), request.telefono(), request.correo());
        return aResponse(clienteRepository.save(cliente));
    }

    public List<ClienteResponse> listar() {
        return clienteRepository.findAll().stream()
                .map(this::aResponse)
                .toList();
    }

    public ClienteResponse buscarPorId(Long id) {
        return clienteRepository.findById(id)
                .map(this::aResponse)
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "Cliente no encontrado"));
    }

    private ClienteResponse aResponse(Cliente cliente) {
        return new ClienteResponse(
                cliente.getId(),
                cliente.getNombre(),
                cliente.getTelefono(),
                cliente.getCorreo(),
                cliente.getFechaCreacion()
        );
    }
}

package com.devsenior.cotiza.cliente;

import java.util.List;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;

import com.devsenior.cotiza.cliente.dto.ClienteRequest;
import com.devsenior.cotiza.cliente.dto.ClienteResponse;

import jakarta.validation.Valid;

@RestController
@RequestMapping("/api/clientes")
public class ClienteController {

    private final ClienteService clienteService;

    public ClienteController(ClienteService clienteService) {
        this.clienteService = clienteService;
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public ClienteResponse crear(@Valid @RequestBody ClienteRequest request) {
        return clienteService.crear(request);
    }

    @GetMapping
    public List<ClienteResponse> listar() {
        return clienteService.listar();
    }

    @GetMapping("/{id}")
    public ClienteResponse buscarPorId(@PathVariable Long id) {
        return clienteService.buscarPorId(id);
    }
}
