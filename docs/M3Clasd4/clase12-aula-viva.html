01 · Punto de partida

El contrato vivo

Una URL debe bastar para que otro equipo entienda cómo consumir la API.

Para pensar

Mañana entra un equipo de frontend a consumir tu API. No tiene acceso a tu código, solo a la URL. ¿Cómo sabe qué endpoints existen, qué datos enviar y qué recibe de vuelta?

Pista: una colección o una reunión dependen de que alguien las mantenga y las comparta.

Ver respuesta

Una API profesional se documenta a sí misma mediante un contrato vivo y siempre actualizado.

La primera reacción suele ser pasar la colección de Postman, explicar por chat o agendar una reunión. Eso no escala ni queda como fuente oficial. El estándar OpenAPI expresa el contrato y Swagger lo convierte en una interfaz que cualquier equipo puede consultar sin tocar el código ni preguntarte.

La promesa de hoy

Convertirás una API que funciona en una API que se puede entregar. Primero elevarás su calidad profesional: documentación automática, validación de entradas y respuestas de error consistentes. Después la empacarás dentro de un contenedor listo para llevar a cualquier servidor.

El punto de partida es gestor-productos: Spring Boot 4.1, Java 17, MySQL y seguridad JWT construida en la Clase 11. El resultado será el estado exacto que pide el integrador del Módulo 3.

02 · Parte 1

El problema real

Funcionar no basta cuando la API todavía depende de quien la construyó.

La API de hoy

  • Solo sabemos qué hace porque nosotros la conocemos.
  • Postman sirve para probar, pero no es el contrato público.
  • Una persona nueva no puede descubrir rutas ni datos esperados.
  • La API confía en todo lo que recibe.

La API que podemos entregar

  • Publica un contrato que otros equipos pueden explorar.
  • Rechaza datos que rompen reglas de negocio.
  • Explica los errores con una forma predecible.
  • Se empaca con el entorno que necesita para arrancar.
!

El riesgo escondido

Hoy nadie comprueba que el precio sea positivo ni que un correo tenga formato real. Un dato inválido puede entrar y contaminar el catálogo.

05 · Documentar

Swagger y OpenAPI

El contrato se genera desde controllers y DTOs, se publica y aprende a usar JWT.

📜OpenAPI

Técnicamente: estándar para describir rutas, métodos, parámetros y respuestas de una API REST en un formato que las máquinas entienden.

🪟Swagger UI

En sencillo: una página web que lee el contrato y lo vuelve una interfaz visual navegable para probar endpoints.

📘En la vida real

Es el manual de un electrodoméstico: no necesitas abrir el aparato para saber qué botones tiene y qué hace cada uno.

i

Contrato y vitrina

OpenAPI es el contrato escrito; Swagger UI es la vitrina que lo muestra y permite probarlo.

La clave: no lo escribimos a mano

springdoc-openapi inspecciona controllers y DTOs y genera el documento OpenAPI automáticamente. Solo agregamos la librería; no redactamos ruta por ruta.

Línea 2.x

  • Corresponde a Spring Boot 3.
  • Un tutorial o la IA puede sugerirla por ser la más común.
  • Con Spring Boot 4 no funcionará bien.

Línea 3.x

  • Es la línea para Spring Boot 4.
  • En esta clase usamos 3.1.0.
  • Verificar compatibilidad evita un error clásico.

public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .requestMatchers("/swagger-ui/**", "/swagger-ui.html", "/v3/api-docs/**", "/v3/api-docs").permitAll()
            .requestMatchers(HttpMethod.GET, "/api/productos/**").permitAll()
            .requestMatchers(HttpMethod.POST, "/api/productos/**").hasRole("ADMIN")
            .anyRequest().authenticated()
        )
        .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
    return http.build();
}

06 · Validar

Nunca confíes en la entrada

Bean Validation convierte las reglas de negocio en anotaciones junto a cada campo.

Para pensar

Alguien envía un producto con nombre vacío, precio -5 y stock -1. Hoy, ¿qué hace nuestra API?

Pista: revisa si existe algo que inspeccione el cuerpo antes de guardarlo.

Ver respuesta

Hoy lo guarda tal cual.

Se suele suponer que Spring lo rechazará o producirá un error, pero nadie está revisando esos datos. Un precio negativo entra a la base y contamina el catálogo. Confiar ciegamente en el cliente es una falla de diseño: nunca se confía en la entrada.

🏷️Definición técnica

Bean Validation, del paquete jakarta.validation, es un estándar de Java para declarar reglas sobre campos mediante anotaciones.

📏Explicación sencilla

En lugar de dispersar if por el código, etiquetas cada campo con la regla que debe cumplir y Spring la revisa.

📝En la vida real

Es el formulario que no te deja enviar hasta que el correo tiene @ y la contraseña es suficientemente larga. La regla vive pegada al campo.

Antes del proyecto

Leer las reglas junto al campo

En una reserva de hotel, @NotBlank exige texto no vacío y @Min exige un valor mínimo. Este ejemplo aislado muestra la sintaxis sin mezclarla todavía con gestor-productos.

Ejemplo aisladoReservaRequest.java
public class ReservaRequest {
    @NotBlank(message = "El nombre del huésped es obligatorio")
    private String huesped;

    @Min(value = 1, message = "Debe reservar al menos 1 noche")
    private int noches;
}

package com.devsenior.gestorproductos.dto;

import jakarta.validation.constraints.*;

public class ProductoRequest {

    @NotBlank(message = "El nombre es obligatorio")
    private String nombre;

    private String descripcion;

    @NotNull(message = "El precio es obligatorio")
    @Positive(message = "El precio debe ser mayor a cero")
    private Double precio;

    @NotNull(message = "El stock es obligatorio")
    @PositiveOrZero(message = "El stock no puede ser negativo")
    private Integer stock;

    @NotNull(message = "La categoría es obligatoria")
    private Long categoriaId;

    @NotNull(message = "La marca es obligatoria")
    private Long marcaId;

    // getters y setters de todos los campos
}
Tipos primitivos

Con int, un campo ausente llega como 0; por eso @NotNull nunca podría detectar la ausencia.

Tipos objeto

Con Integer, un campo ausente llega como null y @NotNull sí lo detecta. Es una decisión de diseño.

i

Getters y setters

Los comentarios marcador se conservan. En IntelliJ se generan con clic derecho → Generate → Getter and Setter; no se escriben uno por uno.

package com.devsenior.gestorproductos.controller;

import com.devsenior.gestorproductos.dto.ProductoDTO;
import com.devsenior.gestorproductos.dto.ProductoRequest;
import com.devsenior.gestorproductos.model.*;
import com.devsenior.gestorproductos.service.ProductoService;
import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import java.util.List;

@RestController
@RequestMapping("/api/productos")
public class ProductoController {

    private final ProductoService productoService;

    public ProductoController(ProductoService s){ this.productoService = s; }

    @GetMapping
    public List<ProductoDTO> obtenerProductos(){
        return productoService.listarProductos().stream().map(ProductoDTO::new).toList();
    }

    @GetMapping("/categoria/{categoriaId}")
    public List<ProductoDTO> obtenerPorCategoria(@PathVariable Long categoriaId){
        return productoService.listarPorCategoria(categoriaId).stream().map(ProductoDTO::new).toList();
    }

    @PostMapping
    public ResponseEntity<ProductoDTO> crearProducto(@Valid @RequestBody ProductoRequest req){
        Producto p = new Producto();
        p.setNombre(req.getNombre());
        p.setDescripcion(req.getDescripcion());
        p.setPrecio(req.getPrecio());
        p.setStock(req.getStock());
        Categoria c = new Categoria(); c.setId(req.getCategoriaId()); p.setCategoria(c);
        Marca m = new Marca(); m.setId(req.getMarcaId()); p.setMarca(m);
        Producto guardado = productoService.agregarProducto(p);
        return ResponseEntity.status(HttpStatus.CREATED).body(new ProductoDTO(guardado));
    }
}

400

Qué error sale ahora

Ante datos inválidos, Spring lanza internamente MethodArgumentNotValidException y responde 400 Bad Request: la petición del cliente está mal formada, no el servidor. El cuerpo predeterminado es enorme y difícil de leer; el siguiente tema le dará una forma limpia.

07 · Responder

Manejo global de errores

Un solo especialista intercepta excepciones y mantiene el mismo formato.

Para pensar

Si cada controller arma su propia respuesta de error, ¿qué pasa cuando la API crece a 40 endpoints?

Pista: piensa en la forma que espera el frontend.

Ver respuesta

Aparecen errores inconsistentes, código repetido y clientes que no pueden anticipar la respuesta.

Cada controller terminaría respondiendo de manera distinta. La solución profesional es centralizar: un solo lugar atrapa los errores de toda la API y los devuelve siempre con el mismo formato.

🎛️@RestControllerAdvice

Componente que intercepta excepciones de todos los controllers y produce una respuesta unificada.

🏢En la vida real

Es la recepción única de quejas: no importa dónde ocurrió el problema, el mismo mostrador responde con el mismo formato.

🧭DRY + SOLID

Los controllers cumplen su tarea; un especialista maneja errores sin repetir lógica.

Paso 01 · Crear

Definir la forma de un error

El cuerpo JSON tendrá un estado, un mensaje, un mapa de errores por campo y una marca de tiempo. El mapa campo → mensaje le dice al cliente exactamente qué falló y por qué.

Archivo: ApiError.java · Ubicación: src/main/java/com/devsenior/gestorproductos/exception/ · Acción: crear; la carpeta exception es nueva.

Crearsrc/main/java/com/devsenior/gestorproductos/exception/ApiError.java
package com.devsenior.gestorproductos.exception;

import java.time.LocalDateTime;
import java.util.Map;

public class ApiError {

    private int status;
    private String mensaje;
    private Map<String, String> errores;
    private String timestamp;

    public ApiError(int status, String mensaje, Map<String, String> errores) {
        this.status = status;
        this.mensaje = mensaje;
        this.errores = errores;
        this.timestamp = LocalDateTime.now().toString();
    }

    public int getStatus(){ return status; }
    public String getMensaje(){ return mensaje; }
    public Map<String, String> getErrores(){ return errores; }
    public String getTimestamp(){ return timestamp; }
}
Paso 02 · Crear

Construir el interceptor central

El primer manejador toma MethodArgumentNotValidException, arma el mapa campo por campo y responde 400. El segundo captura cualquier excepción no prevista y responde 500 con un mensaje genérico.

Archivo: GlobalExceptionHandler.java · Ubicación: src/main/java/com/devsenior/gestorproductos/exception/.

Crearsrc/main/java/com/devsenior/gestorproductos/exception/GlobalExceptionHandler.java
package com.devsenior.gestorproductos.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import java.util.HashMap;
import java.util.Map;

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiError> manejarValidacion(MethodArgumentNotValidException ex) {
        Map<String, String> errores = new HashMap<>();
        for (FieldError fe : ex.getBindingResult().getFieldErrors()) {
            errores.put(fe.getField(), fe.getDefaultMessage());
        }
        ApiError cuerpo = new ApiError(HttpStatus.BAD_REQUEST.value(),
                "Los datos enviados no son válidos", errores);
        return ResponseEntity.badRequest().body(cuerpo);
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> manejarGeneral(Exception ex) {
        ApiError cuerpo = new ApiError(HttpStatus.INTERNAL_SERVER_ERROR.value(),
                "Ocurrió un error inesperado en el servidor", null);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(cuerpo);
    }
}

Detalle de seguridad

El mensaje del error 500 es vago a propósito. Nunca se exponen nombres de clases, líneas ni detalles internos: esa información podría ayudar a un atacante.

08 · Semántica REST

El estado también cuenta la historia

200, 201, 400, 403 y 500 comunican el resultado antes de leer el cuerpo.

Antes

Hasta la Clase 11, crear un producto devolvía 200 OK, el mismo código usado para una consulta exitosa.

Ahora

Crear un recurso responde 201 Created. La semántica distingue creación de consulta.

ResponseEntity permite controlar el código de estado y el cuerpo, en lugar de dejar que Spring elija. Ya está aplicado en ProductoController.

AplicadoProductoController.java
return ResponseEntity.status(HttpStatus.CREATED).body(new ProductoDTO(guardado));

Diseño REST maduro

Un código correcto le dice al cliente qué ocurrió sin obligarlo a leer el cuerpo.

Pregunta de criterio

¿Por qué es mejor devolver 201 al crear en vez de 200, si el cliente igual recibe el producto?

Ver respuesta

Porque el código de estado forma parte del contrato.

Un cliente automatizado puede reaccionar de forma distinta ante 201 —recurso creado— y 200 —consulta exitosa— sin interpretar el cuerpo. La semántica correcta vuelve la API predecible.

09 · Parte 2

Docker: la caja que viaja

La aplicación y su entorno exacto se mueven como una sola unidad portable.

Nuevo problema de negocio

Tu API funciona perfecto en tu computador. La subes al servidor del cliente y no arranca: otra versión de Java, otra configuración. ¿Por qué pasa y cómo se evita?

Pista: instalar a mano no garantiza que dos ambientes queden iguales.

Ver respuesta

Empaquetamos la aplicación junto con su entorno exacto para que corra igual en cualquier lado.

La primera idea suele ser instalar correctamente Java y dependencias en el servidor. Ese proceso es frágil y difícil de repetir: es el clásico «en mi máquina sí funciona». Docker resuelve el problema con un contenedor portable.

📦Definición técnica

Docker empaqueta una aplicación y todo lo necesario para ejecutarla —runtime, librerías y configuración— en una unidad aislada y portable: el contenedor.

🧰Explicación sencilla

Un contenedor es una caja sellada con la app y su entorno. Da igual el servidor: adentro siempre está lo mismo.

🚢En la vida real

El contenedor de barco estandarizó el transporte: encaja en grúas y camiones sin importar qué lleva o a qué puerto llega. Docker hizo eso con el software.

1

10 · Empaquetar

El Dockerfile del backend

Del .jar a una imagen, y de la imagen a un contenedor en ejecución.

Paso 01 · Empaquetar

Construir el archivo ejecutable .jar

Spring Boot puede empacar toda la aplicación en un único archivo ejecutable. Docker tomará ese .jar y lo envolverá con Java adentro. Para agilizar la práctica, el comando omite los tests.

Carpeta: raíz de gestor-productos.

Terminalgestor-productos/
./mvnw clean package -DskipTests
✓

Resultado esperado

Aparece target/gestor-productos-0.0.1-SNAPSHOT.jar.

Paso 02 · Crear

Escribir la receta de la imagen

El archivo va en la raíz del proyecto, sin extensión, con el nombre exacto Dockerfile.

CrearDockerfile · raíz del proyecto
# Imagen base con Java 17 (solo el entorno de ejecución, más liviana)
FROM eclipse-temurin:17-jre

# Carpeta de trabajo dentro del contenedor
WORKDIR /app

# Copiamos el .jar ya empaquetado
COPY target/gestor-productos-0.0.1-SNAPSHOT.jar app.jar

# La app escucha en el puerto 8080
EXPOSE 8080

# Comando que arranca la aplicación
ENTRYPOINT ["java", "-jar", "app.jar"]
Cómo se lee cada instrucción del Dockerfile
InstrucciónQué hace
FROMParte de una imagen oficial con Java 17. La variante -jre, solo ejecución, es más liviana que -jdk.
WORKDIRDefine la carpeta interna donde trabajará la aplicación.
COPYMete el .jar dentro de la imagen y lo renombra app.jar.
EXPOSEDocumenta que la aplicación usa el puerto 8080.
ENTRYPOINTIndica el comando que se ejecuta cuando arranca el contenedor.
Paso 03 · Crear

Excluir lo que no debe entrar

.dockerignore evita copiar código fuente, configuración del IDE y Git. La segunda línea es una excepción: de toda la carpeta target, sí necesitamos el .jar.

Archivo: .dockerignore · Ubicación: raíz del proyecto.

Crear.dockerignore · raíz del proyecto
target/*
!target/gestor-productos-0.0.1-SNAPSHOT.jar
.git
.idea
*.iml
Paso 04 · Construir

Crear la imagen gestor-productos

Carpeta: raíz del proyecto. -t asigna el nombre o tag; el punto final indica que Docker debe usar el archivo de esta carpeta.

Terminalgestor-productos/
docker build -t gestor-productos .
✓

Resultado esperado

Los pasos terminan en Successfully tagged gestor-productos:latest.

Paso 05 · Ejecutar

Levantar un contenedor

Carpeta: cualquiera. -p 8080:8080 conecta el puerto de tu computador con el puerto del contenedor.

TerminalCualquier carpeta
docker run -p 8080:8080 gestor-productos
✓

11 · Configurar

Variables de entorno

La configuración cambia por ambiente; el código y los secretos no deben ir pegados.

Para pensar

¿Debería la contraseña de la base de datos ir escrita fija dentro del .jar que entregas al cliente?

Pista: compara tu computador, el servidor de pruebas y producción.

Ver respuesta

Nunca: los secretos y la configuración que cambia por ambiente se inyectan desde afuera.

La URL y la contraseña no son iguales en desarrollo, pruebas y producción. Quemarlas en el código además crea una fuga de seguridad. Las variables de entorno permiten cambiar valores sin recompilar.

Paso 01 · Editar

Externalizar la conexión

Archivo: application.properties · Ubicación: src/main/resources/ · Acción: reemplazar por esta versión final. Cada variable incluye un valor por defecto para desarrollo local.

Editar · finalsrc/main/resources/application.properties
spring.application.name=gestor-productos

# Datos de conexión: se leen de variables de entorno, con un valor por defecto para desarrollo
spring.datasource.url=${DB_URL:jdbc:mysql://localhost:3306/tienda}
spring.datasource.username=${DB_USER:devsenior}
spring.datasource.password=${DB_PASSWORD:devsenior123}

spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
${ }

Cómo se lee ${VAR:valor}

«Usa la variable de entorno VAR; si no existe, usa el valor que aparece después de los dos puntos». Así local funciona sin preparación adicional y el servidor manda sus propios datos sin recompilar.

Paso 02 · Inyectar

Pasar valores al contenedor

Carpeta: cualquiera. La opción -e entrega los valores cuando el contenedor arranca.

TerminalCualquier carpeta
docker run -p 8080:8080 -e DB_USER=devsenior -e DB_PASSWORD=devsenior123 gestor-productos
✓

Resultado esperado

La aplicación arranca usando esas credenciales sin que queden escritas en el código.

!

Gotcha: localhost cambia de significado

Dentro de un contenedor, localhost es el propio contenedor, no tu computador. Si MySQL está en tu máquina y fuera de Docker, la aplicación no lo encontrará allí.

Docker ofrece el nombre especial host.docker.internal para apuntar al computador anfitrión. Es el error más común al contenedorizar por primera vez: la app «no conecta a la base» porque se dejó localhost.

TerminalMySQL ejecutándose en el host
docker run -p 8080:8080 \
  -e DB_URL="jdbc:mysql://host.docker.internal:3306/tienda" \
  -e DB_USER=devsenior -e DB_PASSWORD=devsenior123 \
  gestor-productos
🔒

Buena práctica pendiente

El secreto JWT todavía está escrito fijo en JwtService. En un proyecto real también se externaliza como variable de entorno, igual que la contraseña de la base.

13 · Criterio senior

La IA como copiloto

Acelera lo mecánico; las decisiones de negocio y seguridad siguen siendo humanas.

Dónde sí acelera

  • Generar getters y setters.
  • Redactar el primer borrador de anotaciones de validación.
  • Explicar una instrucción del Dockerfile.
  • Resolver trabajo mecánico y repetitivo.

Dónde no delegar

  • Decidir qué datos deben validarse.
  • Definir qué rutas necesitan protección.
  • Reemplazar el criterio de negocio.
  • Aceptar una versión sin contrastarla.
AI

Una alucinación muy probable

Si pides la dependencia de Swagger para Spring Boot, la IA puede sugerir springdoc 2.x porque es la línea más común en internet. Con Spring Boot 4 falla: necesitas la línea 3.x.

La regla de validación

Contrasta siempre la versión sugerida con la documentación oficial y con la versión de Spring Boot del proyecto. La IA propone; el ingeniero verifica.
